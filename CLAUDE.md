# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MusicWeb is a synchronized web music server: every connected client listens to the *same* live audio broadcast at the same time, so multiple devices/speakers stay in sync playing the same track. It is not a per-client jukebox — there is one shared playback session for all clients.

## Commands

Run from the repo root (npm workspaces: `server`, `client`).

```bash
npm install                # installs both workspaces

npm run dev:server         # API + WebSocket + audio broadcast, http://localhost:3000
npm run dev:client         # React/Vite dev server, http://localhost:5173 (proxies /api and /ws to :3000)

npm run build:client       # production build of client/dist
npm start                  # runs the server, which serves client/dist if it exists (production mode)
```

There is no test suite yet. There is no linter configured.

Server-only commands (run inside `server/`): `npm run dev` (node --watch) or `npm start`.

## Architecture

Two workspaces, no shared code between them: `server/` (Node/Express/ws/SQLite) and `client/` (React/Vite). The client talks to the server over two independent channels — understanding why there are two, and what each does, is the key to working on this codebase.

### 1. Control channel — WebSocket (`server/src/wsServer.js` ↔ `client/src/hooks/useSocket.js`)

Carries **no audio**, only JSON playback state: `{ track, isPlaying, positionSeconds, shuffle, repeat, crossfadeSeconds, upNext, queue }` (`upNext`/`queue` are arrays of *resolved track objects*, not ids — see queue playback below). On connect, a client receives the current state; every `playQueue`/`next`/`pause`/`resume`/`stop`/`seek`/`enqueueNext`/`removeFromUpNext`/`reorderUpNext`/`shuffle`/`repeat`/`crossfade` command from *any* client is applied to the single shared `playbackState` (`server/src/playbackState.js`), which then notifies `wsServer.js` (via `onChange`, see below) to rebroadcast the resulting state to *all* connected sockets. This is what keeps every client's UI (and, indirectly, its `<audio>` element) showing the same track/position/play-state/queue. There is no concept of per-client state or a "host" client — any client can control playback for everyone, **including scrubbing the progress bar**: a seek from one client moves the position for all of them, the same as play/pause/skip.

`playbackState.js` exposes `onChange(fn)` rather than `wsServer.js` calling `broadcastState()` directly after handling a message, because not every state change originates from an incoming WS message — a playlist auto-advancing to its next track fires on a `setTimeout` inside `playbackState.js` itself (see queue playback below). `onChange` is the hook that lets a server-internal timer still reach every client.

### 2. Audio channel — per-track file streams with Range support

There are two audio endpoints, and which one the player uses matters:

- **`GET /api/tracks/:id/audio`** — a *stable, per-track* URL. **This is what the player actually plays.** It exists because a crossfade has to fetch the *next* track's bytes while the current one is still sounding, which `/api/stream` can't express. Cacheable (`public, max-age=86400`): keyed by track id, the content is immutable.
- **`GET /api/stream`** — the current track, whatever that is right now (`Cache-Control: no-store`, since this URL's *meaning* changes every time the session moves on). Still served, and still the honest answer to "give me what's playing", but **no client code uses it any more** — `PlayerBar.jsx` and `useTrackWaveform.js` both moved to per-track URLs. `broadcast.js`'s subscriber bookkeeping (`startBroadcast`/`pauseBroadcast`/`resumeBroadcast`) consequently operates on an empty set in normal use; it is kept because the endpoint is kept, not because the player needs it.

Both are served by `openRangeStream()` in `server/src/fileRange.js`, which handles the shared part: **always starting from byte 0** unless the client sent an explicit `Range`, and supporting standard HTTP `Range` requests (`Accept-Ranges: bytes`, 206 responses with `Content-Range`, 416 for an unsatisfiable range, and an `end` clamped to the file size). Each request gets its own `fs.createReadStream` piped straight to its response — deliberately *not* one shared pipe fanned out to everyone: a local file read finishes far faster than any client can connect (a whole song can drain to disk-read EOF in milliseconds on localhost), so a single shared stream would hit EOF and tear itself down before most clients ever arrived. Independent per-client streams sidestep that.

Starting every response at byte 0 is not optional: `.mp3`/`.wav`/`.opus` each need their leading container bytes to decode at all (ID3 tag, RIFF header, Ogg identification page) — serving a computed mid-file offset instead (an earlier version of this code did that, to make "join mid-track" work) reliably broke playback in every browser (Firefox: `NS_ERROR_DOM_MEDIA_METADATA_ERR`) because the decoder never saw a valid header. **If sound stops playing again, check first whether something reintroduced a `start` offset into the no-Range path of `openRangeStream()` in `fileRange.js`.**

"Join mid-track" (and scrubbing the progress bar — same mechanism) is handled the standard HTML5-audio way: `useAudioDecks.js` sets `el.currentTime = state.positionSeconds` (once on `loadedmetadata` when a deck loads a track mid-flight, and on every subsequent state broadcast if the active deck drifts by more than ~1.5s — the drift-correction effect), and the browser converts that into its own Range request. `playbackState.seek(positionSeconds)` (triggered by the WS `seek` command, itself from dragging/clicking `PlayerBar.jsx`'s progress bar) only updates the server's own position bookkeeping (`elapsedBeforeStart`/`startedAt`) and reschedules the auto-advance timer — it never touches the audio endpoints, because seeking within the *same* file needs no new connection, just the browser's own Range request against the resource it already has open. Consequences to keep in mind when touching this code:

- **Actual play/pause is enforced client-side.** `useAudioDecks.js` calls `play()`/`pause()` on the active deck based on `state.isPlaying` from the WebSocket — that's the real pause. Pausing also *settles* any running crossfade (active deck to full gain, other stopped) rather than leaving a ramp animating against a silent session. Server-side `pauseBroadcast()`/`resumeBroadcast()` act on `/api/stream` subscribers, of which there are normally none — they are not part of playback correctness.
- **A track change swaps decks; it does not reload one.** The incoming track goes into the idle deck (already preloaded, see `PlayerBar.jsx` below) and that deck becomes active. There is no "reconnect every listener" step any more: each deck holds its own per-track URL, so a different file means a different request that was already opened ahead of time, not a new `Content-Type` spliced into an in-flight response.
- `openRangeStream()` sets an explicit `Content-Length` (from `fs.statSync`) rather than chunked transfer — browsers rely on it (plus `Accept-Ranges`) to build a working seek bar and to know a track's byte size for computing Range requests.
- Sync is "same content, same approximate position," not sample-accurate — client-side buffering/decoding can still cause small drift between devices. If tighter sync is ever needed, that's a client-side clock-alignment problem (nudging `currentTime` toward the WS-reported `positionSeconds`), not something to solve server-side.

`playbackState.js` is the single source of truth for *what* is playing and *when* it started; the audio endpoints only serve bytes. Track changes flow: WS command → `playbackState` → broadcast of the new state → each client's `useAudioDecks` swaps decks.

### Queue playback (continuous looping context + a non-looping priority queue)

`playbackState.js` tracks the upcoming order as **two lists** with fundamentally different lifetimes:

- `upNext` — track ids the user explicitly queued via the right-click "Ajouter à la file" context menu (WS `enqueueNext`), always played *before* anything else, and **consumed for good** — once one of these plays, it's gone, never re-added anywhere. `enqueueNext(trackIds)` prepends (`[...newIds, ...upNext]`), so the most recently queued batch plays first — each call inserts right after the current track, same convention as a normal media player's "play next." Fully user-orderable: `reorderUpNext(newOrderIds)` replaces the list outright (rejected if it isn't a permutation of the current one — defends against a stale client) and `removeFromUpNext(trackId)` drops one entry. If nothing is playing when tracks are enqueued, the first one starts immediately and the rest become `upNext`.
- `defaultQueue` — the rest of the current **context** (a whole playlist, or the *entire library*) in playback order, and **loops**: `playQueue(trackIds)` is the only entry point that sets this up (see below — both playlist and library playback funnel through it), and it's the sole "start playing" command left; there's no more separate single-track play with no follow-up.

**The loop is the core mechanic**, in `advanceQueue()`: whenever a track finishes (naturally, or via manual skip) and it came from `defaultQueue` (tracked by `state.currentSource`, `'queue'` vs `'upNext'`), it's pushed onto the *back* of `defaultQueue` before picking what plays next — so a playlist or the whole library just keeps cycling forever, "jouer en continu," instead of running out. A track that came from `upNext` is never pushed back anywhere when it ends — that's the entire difference between the two lists. Priority is still `upNext` first, `defaultQueue` second, regardless of where the *previous* track came from: the loop-back happens unconditionally for a finishing `'queue'` track even if what plays next is a priority `upNext` item. **No deduplication**: queuing a track via `enqueueNext` that's *also* still sitting in `defaultQueue` will play it twice — once from `upNext`, once again when the loop reaches its own copy. This matches Spotify's "Play Next," not a bug.

`state.baseOrder` is the **static** canonical (unshuffled) order of the *entire* context, snapshotted once at `playQueue()` time and never mutated by playback — nothing is ever permanently removed from a looping context, so there's nothing to keep pruning from it (this is a deliberate simplification from an earlier version that shrank `baseOrder` as tracks were consumed, which doesn't make sense once tracks loop back). **Shuffle** (`state.shuffle`, WS `shuffle` → `setShuffle(enabled)`) only ever touches `defaultQueue`, never `upNext`: turning it on Fisher-Yates-shuffles `defaultQueue` in place; turning it off recomputes `defaultQueue` as `baseOrder` filtered down to whatever ids are currently in it (restores canonical relative order without inventing or losing tracks).

Auto-advance is a `setTimeout` (`scheduleAdvance`/`advanceQueue`) sized to the current track's remaining duration *minus `crossfadeSeconds`* (`track.duration - elapsedBeforeStart - crossfade`, the lead ignored when it exceeds the track's own length), re-armed by `resume`/`seek`/`enqueueNext`/`repeat`/`crossfade` so it always reflects the real remaining time. It only ever exists while something is actually playing: `pause` clears it outright, and `scheduleAdvance()` returns early when `isPlaying` is false, so the callers that *can* run mid-pause (`seek`, `enqueueNext`) don't arm one behind a paused session — a timer surviving a pause would fire `advanceQueue()` on its own and restart playback for every device. `resume` recomputes it from the real remaining time, so nothing is lost by not arming it earlier. A manual skip is the same `advanceQueue()` function, exposed as the WS `next` command / the skip-forward button in `PlayerBar.jsx` (enabled whenever `upNext.length + queue.length > 0`).

**Crossfade** (`state.crossfadeSeconds`, WS `crossfade` → `setCrossfade(seconds)`, 0–12s, 0 = off) is **shared state, not a per-device preference, and that is the whole point.** A real crossfade needs the next track to start before the current one ends; a client doing that on its own would run ahead of the server's timeline by exactly the crossfade length and drift out of sync with every other speaker — which is the one thing this app exists to prevent. Shared, the server advances early by the same amount for everyone, the shared state switches simultaneously on all devices, and each client merely keeps playing the *outgoing* track's remaining tail locally while fading it under the incoming one. Sync is preserved because nobody is ahead of anybody. (Volume stays per-device by contrast: it changes nothing about *when* anything happens.)

Client side, `QueueView.jsx` (reachable via the "File d'attente" sidebar nav item, which doubles as a drop target — see `Sidebar.jsx`) is where `upNext` gets reordered: each row is draggable with its own DnD mimetype (`application/x-musicweb-upnext-reorder`, distinct from `TrackRow.jsx`'s `TRACK_DND_TYPE`) carrying the source index; dropping computes the new order via array splice and sends the whole list through `reorderUpNext`. `defaultQueue` tracks and the current track are shown read-only in the same view (that's the "see what's coming up" half of the feature) — they're never targets for reordering, only `upNext` is.

### Library & storage

- Audio files live on disk in `server/music/` (gitignored except `.gitkeep`).
- Metadata (title/artist/album/duration/cover art) lives in SQLite (`server/data/library.sqlite`, gitignored), managed with `better-sqlite3` — synchronous, no query builder/ORM. Playlists are two more tables: `playlists` and a `playlist_tracks` join table (`playlist_id, track_id, position`), with `ON DELETE CASCADE` (needs `PRAGMA foreign_keys = ON`, set once in `db.js`) so deleting a playlist drops its membership rows automatically. `server/src/playlists.js` holds the prepared statements and helpers (`createPlaylist`, `addTrackToPlaylist`, …); `server/src/routes/playlists.js` is the plain CRUD REST surface for the client to browse/build playlists, plus M3U export (`GET /api/playlists/:id/m3u`) and import (`POST /api/playlists/import`). Export writes entries as absolute URLs back to this server (built from the request's own `Host`, since the server can't know which of its addresses the client reached it on) so the file plays as-is in VLC on any device on the LAN — and so the importer gets an exact track id to match on. `server/src/m3u.js` does the building and parsing; import resolves each entry exact-to-fuzzy (our own track-id URL → exact filename → case-insensitive filename → the `#EXTINF` label against "artist - title") and reports what it couldn't match rather than dropping it silently. Import always creates a *new* playlist: importing twice gives two playlists, which is undoable, whereas merging into an existing one is not. *Playing* one doesn't go through this REST surface at all — the client already has the playlist's tracks loaded for display (`PlaylistView.jsx`), so it sends that array straight through the WS `playQueue` command; the server has no playlist-specific playback code.
- `server/src/library.js` both scans `server/music/` on server startup (`scanLibrary`, called from `index.js`) and indexes files uploaded via `POST /api/upload` (`multer`, writes into `server/music/` with a random filename, extension preserved). Tag extraction uses `music-metadata`, including embedded cover art (`common.picture[0]`), stored as a `BLOB` + `cover_mime` column directly in the `tracks` row.
- Cover art bytes are deliberately excluded from every list/lookup query (`TRACK_COLUMNS` in `library.js` selects `(cover IS NOT NULL) AS hasCover` instead of the blob) so `GET /api/library` stays cheap — the actual image is only fetched per-track via `GET /api/tracks/:id/cover` (`getTrackCover`), which clients request directly as an `<img src>` when `hasCover` is truthy.
- `INSERT OR IGNORE` on `filename` means re-scanning never duplicates or updates existing rows — if you change indexing logic, deleting the sqlite file is the simplest way to force a full re-index.
- Playlists also have a `cover`/`cover_mime` BLOB pair (user-uploaded, unlike a track's cover which comes from the audio file's own tags), following the same `hasCover`-flag-in-listings / dedicated-route-for-bytes pattern (`POST`/`GET`/`DELETE /api/playlists/:id/cover`, `multer.memoryStorage()` capped at 5MB, `COVER_MIME_TYPES` in `routes/playlists.js` restricts to jpeg/png/webp/gif). Because `playlists` predates cover support, `db.js` runs a small one-time `ALTER TABLE ... ADD COLUMN` migration guarded by `PRAGMA table_info(playlists)` — `CREATE TABLE IF NOT EXISTS` alone doesn't add columns to a table that already exists, which an already-running install's `library.sqlite` will be. Client side, unlike a track cover (immutable once indexed), a playlist cover can be replaced at any time, so `PlaylistView.jsx` appends a `coverVersion` counter as a `?v=` query param after every upload/removal to bust the browser's `Cache-Control: public, max-age=86400` — without it the old image would keep showing for up to a day after a change.

### Client structure

Spotify-style layout: a fixed left `Sidebar.jsx` (library link + queue link + playlist nav + inline "new playlist" form), a scrollable `main` content area that swaps between `Library.jsx`, `PlaylistView.jsx`, and `QueueView.jsx`, and a `PlayerBar.jsx` fixed to the bottom of the viewport (`position: fixed`, hence `.main` has bottom padding in `index.css` so content doesn't sit underneath it).

`App.jsx` is where this is wired together. It owns two pieces of state that both `Sidebar.jsx` and the main-content components need: `playlists` (the list with track counts, fetched via `refreshPlaylists()`) and `view` (`{ type: 'library' }`, `{ type: 'playlist', id }`, or `{ type: 'queue' }` — decides which main-content component renders; there's no router, this is the entire navigation model). `refreshPlaylists` is passed down as a callback (`onTrackRemoved`, or called directly after create/delete/add-track) so any component that mutates playlist membership can make the sidebar's track counts catch up, without each component fetching its own independent copy.

- `Sidebar.jsx` — navigation, playlist creation/deletion, **and the drop target for adding tracks to a playlist**: each playlist `<li className="playlist-nav-item">` has `onDragOver`/`onDrop` handlers reading a JSON array of track ids off `e.dataTransfer` (`TRACK_DND_TYPE` constant, exported from `TrackRow.jsx`) and calls `onDropTrack(playlistId, trackIds)` (→ `App.jsx`'s `addTracksToPlaylist`, one `POST /api/playlists/:id/tracks` per id, no bulk-add endpoint). `dragOverId` drives the `.drag-over` highlight. The "File d'attente" nav item is a drop target too, reading the same `TRACK_DND_TYPE` payload and calling `onDropQueue` (→ `enqueueNext`) — dragging onto it is the direct equivalent of the row menu's "Ajouter à la file", which remains the only route on touch.
- `TrackRow.jsx` — shared row markup for both `Library.jsx` and `PlaylistView.jsx` (index, cover-or-placeholder, title/artist, duration). Two things happen on a row: **drag** (`onDragStart` puts a JSON-encoded array of track ids on `dataTransfer` under `TRACK_DND_TYPE`, for dropping onto a playlist in the sidebar) and **right-click** (`onContextMenu`, `e.preventDefault()`'d, opens a small menu — see `ContextMenu.jsx` — with a single "Ajouter à la file" action wired to `enqueueNext`). Both act on `dragIds`: the whole multi-selection if the row is part of one, otherwise just that row (see selection below). A left-click plays — not just that one track, but the *whole list it's part of*, rotated to start there (`playFrom` in `Library.jsx`/`PlaylistView.jsx`, sent via the shared `onPlay` prop → WS `playQueue`); this is what makes clicking anywhere in the library or an open playlist start continuous playback through the rest of it. A `children` slot carries whatever trailing action differs between the two lists (currently just `PlaylistView.jsx`'s remove button — `Library.jsx` doesn't pass any).
- `ContextMenu.jsx` — generic floating menu positioned at click coordinates; closes on outside click or Escape. Currently only ever rendered with one item, but it's not hardcoded to that — a second track-row action would just be another entry in the `items` array `Library.jsx`/`PlaylistView.jsx` pass in.
- `hooks/useTrackSelection.js` — multi-selection shared by `Library.jsx` and `PlaylistView.jsx`, file-manager conventions: plain click plays and collapses the selection to none, Ctrl/Cmd+click toggles one track without playing, Shift+click selects the contiguous range from the last click. `dragIdsFor(trackId)` is what both drag and right-click use to resolve "which tracks does this row's action apply to." `PlaylistView.jsx` is mounted with `key={playlistId}` in `App.jsx` specifically so switching playlists remounts it and resets this hook's state — without that, a selection could persist across playlists and highlight unrelated tracks that happen to share an id.
- `PlaylistView.jsx` — has the "Lire" button, which sends the *unrotated* full playlist through the same `onPlay`/`playQueue` path as clicking a row inside it (rotated) — both are "play this context," just starting at a different point. Also owns the cover-art upload UI: the cover square is a `onClick`-triggered hidden `<input type="file">` (no drag-and-drop here, unlike everything else in this app — a single click target was simpler for a one-off "pick an image" action), with a hover overlay for the affordance and a remove button that only appears once a cover exists.
- `QueueView.jsx` — read-only current track, then the `upNext` list (reorderable by drag, removable, see the queue-playback section above for the DnD mimetype) followed by the read-only `queue` (context) list. It is deliberately not itself a drop target: `Library.jsx`/`PlaylistView.jsx` and `QueueView.jsx` are mutually exclusive `view`s and can never be on screen at once, so there'd be nothing to drag *from*. Dropping onto the sidebar's queue nav item (see `Sidebar.jsx`) is the reachable version of that idea.
- `PlayerBar.jsx` — the two `<audio>` elements live here, but all the logic about when each loads, plays, seeks and fades is in `hooks/useAudioDecks.js`. **Two decks, not one**, because a crossfade needs the outgoing track still sounding under the incoming one, which a single element cannot do. On a track change the incoming track goes into the *idle* deck and that deck becomes active; the outgoing one either fades out over `crossfadeSeconds` or is cut immediately. The choice between the two is a heuristic on the outgoing deck's own remaining time: within `crossfadeSeconds + 2s` of its end it was a natural end and gets a fade, otherwise it was a skip/seek/manual pick and fading a song out from the middle would sound like a bug. The idle deck preloads the next track ~15s before it's needed, and is never touched while it's still sounding (mid-crossfade the idle deck is the one fading *out*). It tracks a local `currentTime` via the `timeupdate` event to drive the progress bar, independent of the WS-pushed `positionSeconds` (which only updates on state changes, not continuously) — `state.track.duration` (from tag metadata) is used as the total, not `audio.duration`. It also has the shuffle toggle (WS `shuffle`) and the skip button (enabled via `upNext.length + queue.length > 0`). It also owns **volume**, which is deliberately *not* part of the shared WS state: each connected device is its own physical speaker, so volume is a per-device `<input type="range">` bound straight to `audio.volume`, persisted to `localStorage` (`musicweb-volume`) so it survives a reload.
- `icons.jsx` — small hand-written inline SVG icon components (no icon library dependency); `format.js` — the one shared `formatTime(seconds)` helper.
- `NowPlayingBars.jsx` — the small animated-equalizer indicator shown in place of the track index for whichever row is currently playing (`TrackRow.jsx` when `active`; `QueueView.jsx`'s current-track `QueueRow` via its `current`/`isPlaying` props). Freezes (doesn't animate) when `isPlaying` is false rather than disappearing, so a paused track is still visually marked as "this one."
- `toast.js` + `ToastHost.jsx` — a deliberately tiny module-level pub/sub (`showToast(message)` / `onToast(fn)`) instead of React Context, because toasts are fire-and-forget from action handlers, not state anything needs to read back. `ToastHost.jsx` is mounted once in `App.jsx` and is the sole subscriber; any module can call `showToast()` directly without threading a callback prop through the tree. Used for the two actions that otherwise give no feedback at all — adding to a playlist and adding to the queue (both called from `App.jsx`'s `addTracksToPlaylist`/`enqueueNext`, not from the components that trigger them, so there's one place to word the message using the `playlists` list already in state).
- Library search (`Library.jsx`): a local `query` state filters the rendered rows client-side (title/artist substring match) — `useTrackSelection` is initialized with the *filtered* list, not the full one, so Shift+click range-selection matches what's visually on screen. Clicking a filtered row still queues the *whole* unfiltered library rotated to start there (`playFrom` looks up the index in `tracks`, not `filtered`) — the search is a lens for finding a track, not a way to narrow what plays afterward.
- Spacebar play/pause is wired in `App.jsx` (a single `document`-level `keydown` listener, not per-component) since it needs to work regardless of which view is showing; it's ignored while an `<input>`/`<textarea>`/contenteditable element has focus so it doesn't fight with typing in the search box or the new-playlist field.

There's no client-side state management library — `useSocket()`'s `state` is the entire shared playback state tree; `playlists`/`view` in `App.jsx` is the rest.

## Known limitations (by design, for now)

- Single global playback session — no rooms/multi-session support.
- No auth — any client on the network can control playback, edit any playlist, etc.
- `.opus` uses `audio/ogg; codecs=opus`, which Safari does not support in `<audio>` — mp3/wav are the safe cross-browser choice if that matters.
- Every drag-and-drop path is native HTML5 DnD, so none of them work on touch devices. *Adding* a track to a playlist or to the queue does have a tap fallback (the always-visible "more" button on every row, `TrackRow.jsx`, which opens the same menu as a right-click); *reordering* has none — a playlist's own stored track order (`PlaylistView.jsx`) and the `upNext` order (`QueueView.jsx`) can only be changed by dragging.
- Playlist reordering is only offered while that playlist's sort is `'custom'` (`sortBy === 'custom'` gates `TrackRow`'s `reorderable` prop). Any other sort is a read-only view *derived* from the stored order, so dragging in it would have no well-defined meaning — there'd be no way to map a drop position back onto the underlying order.
- `enqueueNext`/manually queuing a track that's *also* still in the current context's `defaultQueue` doesn't deduplicate — it will play twice (once from `upNext`, once again when the loop reaches its own copy). Matches how Spotify's "Play Next" behaves, not considered a bug.
- `repeat: 'off'` ends a context by calling `stop()`, which wipes `track`/`upNext`/`defaultQueue`/`baseOrder` outright — so playing through a playlist once leaves nothing behind at all (no paused last track, no queue to restart from), rather than settling into a "finished, ready to replay" state.
